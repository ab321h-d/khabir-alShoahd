# توصية الاستضافة بعد فك الارتباط

## القرار المقترح

يوصى بأن تكون **Cloudflare Pages** هي الاستضافة الأولى لإصدار «خبير الشواهد» المستقل. التطبيق الحالي عبارة عن React/PWA محلي البيانات؛ إذ تحفظ الشواهد والتقييمات داخل متصفح المستخدم ولا يحتاج الإصدار الحالي إلى قاعدة بيانات سحابية أو خدمة خادمية دائمة. لهذا فإن استضافة الملفات الثابتة عبر شبكة CDN عالمية هي الخيار الأقل تعقيدًا والأقرب لطبيعة المنتج.

توفر خطة Cloudflare Pages المجانية عددًا غير محدود من المواقع والطلبات الثابتة والنطاق الترددي، مع 500 عملية بناء شهرية و100 نطاق مخصص للمشروع. كما تدعم النطاقات المخصصة وHTTPS تلقائيًا. [1] [2]

| المنصة | الملاءمة للتطبيق | الخطة المجانية أو البداية | الملاحظة العملية |
|---|---|---|---|
| **Cloudflare Pages** | **الخيار الموصى به** لتطبيق PWA ثابت ومحلي البيانات | طلبات ونطاق ترددي ثابتان بلا حد منشور، و500 build شهريًا | أفضل توازن بين الأداء والتكلفة؛ اختر نطاقًا فرعيًا أولًا إن لم ترغب في نقل خوادم الأسماء. [1] [2] |
| Netlify | بديل سهل بواجهة نشر مريحة | Free دائمًا، نطاقات مخصصة مع SSL، وحد شهري 300 credit | مناسب إن فضّلت تجربة النشر والبناء المباشرة في Netlify؛ راقب حد الاستخدام الشهري. [3] |
| Render Static Sites | بديل مجاني عملي | نشر المواقع الثابتة مجاني، مع Git/CDN/TLS والنطاق المخصص | جيد إذا توسع التطبيق لاحقًا إلى خدمة Node أو قاعدة بيانات ضمن المنصة نفسها. [4] |
| Vercel | جيد تقنيًا، لكن ليس الاختيار الأول للتسويق التجاري | Hobby مجاني | خطة Hobby مخصصة للاستخدام الشخصي غير التجاري؛ عند التسويق المدفوع أو البيع انتقل إلى Pro أو اختر Cloudflare/Netlify/Render. [5] |
| GitHub Pages | مناسب للعرض التجريبي أو المشروع المفتوح المصدر | HTTPS ونطاق مخصص مدعومان | لا أوصي به للإصدار التجاري؛ صفحات GitHub Pages منشورة للعامة حتى عند ارتباطها بمستودع خاص وفق شروط الخطة. [6] |
| DigitalOcean App Platform | بديل منخفض التكلفة قابل للتوسع | حتى 3 تطبيقات ثابتة مجانًا مع 1 GiB نقل لكل تطبيق | خيار جيد عندما تحتاج لاحقًا إلى حاوية أو API مدفوع بخطة شهرية واضحة، لكنه ليس أوفر من Cloudflare للتطبيق الحالي. [7] |

> **الخلاصة:** ابدأ بـ **Cloudflare Pages + GitHub + نطاقك الخاص**. لا تنتقل إلى خادم أو قاعدة بيانات إلا إذا أضفت لاحقًا حسابات مركزية، استقبال ملفات بين الأجهزة، أو تحليلات تتطلب خادمًا.

## خطة الانتقال العملية

| الخطوة | الإجراء | النتيجة المتوقعة |
|---|---|---|
| 1 | تنزيل الشفرة كـ ZIP ثم رفعها إلى مستودع GitHub خاص بك | ملكية مستقلة للكود وسجل نسخ واضح |
| 2 | إزالة إعدادات المنصة والملفات الخاصة بها، مع الإبقاء على React وVite وPWA وIndexedDB | مشروع مستقل قابل للنشر في أي خدمة متوافقة مع Node/Vite |
| 3 | إنشاء مشروع Pages جديد وربط GitHub | نشر تلقائي مع كل تحديث للكود |
| 4 | استخدام أمر البناء `pnpm build` ومجلد النشر `dist/public` | نشر ملفات PWA النهائية مع service worker وmanifest |
| 5 | ربط النطاق الفرعي مثل `app.example.sa` عبر CNAME أولًا | انتقال بسيط بلا حاجة لنقل إدارة DNS كاملة [2] |
| 6 | عند الحاجة إلى النطاق الجذري مثل `example.sa`، أضف النطاق كمنطقة Cloudflare ووجّه خوادم الأسماء إليه | تهيئة النطاق الجذري وفق متطلبات Pages [2] |
| 7 | تحقق من HTTPS، وتحقق من الفتح المباشر لمسار `/director`، وتجربة التطبيق دون اتصال، وتصدير PDF/Word/Excel | ضمان بقاء PWA ووضع الخصوصية المحلي بعد النقل |
| 8 | قبل إعلان الرابط الجديد، يصدّر المستخدمون نسخهم المحلية ويحتفظ المدير بملفات PDF وتقارير Excel | تقليل خطر فقد بيانات IndexedDB المرتبطة بالنطاق القديم |

## ضوابط مهمة

لا تضع ملفات مستخدمين أو بيانات سرية داخل مستودع Git أو داخل حزمة التطبيق. احتفظ بخيار النسخ الاحتياطي المحلي، واعرض للمستخدم عند الإطلاق على النطاق الجديد تنبيهًا يوضح أن البيانات القديمة تبقى في المتصفح والنطاق القديمين حتى يتم تصديرها واستيرادها يدويًا.

لا يحتاج التطبيق الحالي إلى خادم مدفوع دائم التشغيل. إذا تم لاحقًا اعتماد تسجيل دخول مركزي أو رفع ملفات بين المعلم والمدير أو قواعد صلاحيات، يمكن الإبقاء على Cloudflare وإضافة Workers/D1/R2، أو الانتقال إلى Render أو DigitalOcean وفق الحاجة إلى خادم Node وقاعدة بيانات.
